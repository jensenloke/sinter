# Sinter v0.3.0

Sinter v0.3.0 adds exact same-harness instance routing and direct encrypted session transfer between devices, while keeping the CLI local-first and usable without an account.

## Multiple instances of one harness

Configure several stores for the same harness—such as personal Claude Code and `claude-addvita`—and address them independently as `claude@personal` and `claude@addvita`.

- Scans, reads, writes, ports, resume commands, metadata, lineage, TUI actions, and GUI actions follow the exact instance.
- Identical native session IDs can safely exist in different stores.
- Existing single-store configurations continue to use the `default` instance.
- Legacy ledgers migrate transactionally to the new `(harness, instance, native-id)` identity without changing native harness stores.

```sh
sinter scan --profile all
sinter port claude@personal:<id> --to claude@addvita --profile all
sinter resume claude@addvita:<id> --profile all --exec
```

## Direct encrypted device transfer

Move conversation context directly over a local network or Tailscale with the new `receive` and `send` commands:

```sh
# Receiving device
sinter receive --to claude@addvita

# Sending device: use the one-time locator printed by the receiver
sinter send <id> --to 'sinter://transfer/v1?...'
```

Each locator is short-lived and one-use. Payloads are encrypted and authenticated end to end, and the sender reports success only after the receiver validates, approves, and imports the session. No SSH daemon, Sinter account, or cloud relay is required.

Network transfers intentionally exclude raw adapter records, provider-private state, native store paths, additional workspace directories, repository files, and credentials. This release transfers conversation context—not the working tree.

## Reliability

- Concurrent scans now use complete, transactional snapshots and cannot ghost sessions from another named instance.
- Adapter registry bindings preserve instance identity across detection, scanning, carry-aware reads, writes, and custom resume commands.
- Encrypted transfers reject oversized, expired, replayed, malformed, or unauthenticated requests and return authenticated acceptance receipts.
