# Sinter v0.4.1

Sinter v0.4.1 completes signed device-enrollment waiting and adds an explicit,
synthetic-only two-device capsule diagnostic while keeping session uploads and
Cloud storage disabled.

## Device enrollment

- `sinter devices register` now waits for an existing active device to approve a
  subsequent-device request, then verifies and saves the approved device ID.
- `--no-wait` retains the script-friendly approval-required response, while
  `--timeout` bounds waiting between five seconds and fifteen minutes.
- Ctrl+C stops only the local wait. It does not delete the enrollment request or
  locally generated keys.

## Synthetic capsule diagnostic

Approved private-alpha members with two active registered devices can verify the
local capsule envelope without reading a session:

```sh
sinter devices capsule-test create --output ./sinter-capsule-test.json
# Manually copy the file to the other registered device.
sinter devices capsule-test open --input ./sinter-capsule-test.json
```

- Create encrypts one fixed synthetic SIF fixture for the current active
  exact-suite device registry, self-decrypts it, proves same-process replay
  rejection, and exclusively creates a `0600` file without following or
  overwriting an existing path.
- Open safely reads a bounded regular file, requires both the local recipient and
  signed sender to remain active, verifies the exact fixture, and proves replay
  rejection.
- Neither command scans native harness stores, opens the Sinter ledger,
  bootstraps profile configuration, uploads the file, or emits private keys,
  ciphertext, device names, account data, or decrypted fixture content.
- Human and JSON output contain only capsule/file identifiers, fingerprints,
  recipient count, file SHA-256, and verification booleans.

## Verification and boundaries

The release gate passed 832 tests and 9,680 assertions, both TypeScript checks,
CLI and Cloud production builds, package inspection, isolated Bun/npm global
installs, and the built CLI help smoke test. The identical packaged candidate
then created the fixed fixture on the MacBook and opened it on the enrolled Mac
Mini: capsule IDs and file hashes matched, both device fingerprints were
distinct, exact-fixture decryption passed, and replay was rejected.

This diagnostic is not durable replay protection and does not enable Cloud
capsule storage, inbox, relay, sync, or real-session uploads. Human cryptographic
review and durable replay remain required before freezing the capsule format or
adding Storage.
